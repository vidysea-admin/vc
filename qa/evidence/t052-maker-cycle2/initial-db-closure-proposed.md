## Actual source race

Fresh creation installs an initially empty origin, inserts the immutable proof, inserts the immutable baseline, then performs the one exact readiness association CAS. These are separate acknowledged original operations. A concurrent open retry can read the correct same-capability provisional origin before association, then read the newly visible standalone fresh proof. Current lines 930-934 derive a root ID from that proof even though the captured session has no readiness association. The next root read can occur before the creator inserts the root and line 941 reports corruption. If the root already exists, the later fresh validator can instead reject the old session snapshot for lacking its derived associations. Both are manifestations of treating standalone fresh evidence plus a stale origin snapshot as readiness.

The D048 linearization point remains the persisted session association CAS. Standalone proof/root visibility is not readiness, is not completed creator success, and does not permit a retry to mint or adopt evidence.

## Preserved safety and risks

The observer consumes the creator's actual persisted shared admission, never its unacknowledged raw session visibility. Its generation and creationAttempt remain pinned to the original winner across every observation. A recreated same-key session cannot satisfy that origin selector; its association/proof tokens cannot be substituted. Original grant loss stays latched and a replacement grant never refreshes authorization. B/C and historical rows retain complete raw bytes.

The important deliberate limit is between observing and admitting. Parent clarified that valid same-capability open retries must observe the persisted winner across ALL successful interleavings, including receipt not yet visible. Therefore the exact server-capability-bound lifecycle retry can await shared readiness before the proof exists, without treating the capability as proof or exposing success. General provisional consumers still HOLD. This reconciles the unchanged B23 concurrent-open positive with the unchanged D048 ordinary provisional HOLD control. It is a narrowly reviewed clarification of when a lifecycle observer waits, not a proof-adoption exception or authority expansion.

Root/proof creation is sequential, so the observer must not report corruption solely for absence of a not-yet-claimed root. Conversely, once association is actually present, root/proof absence is actual claimed corruption. Repeating from a refreshed snapshot is essential: retaining the old binding/session tuple while merely retrying root reads would reproduce the bug or admit partial association. Deadline waiting must not introduce hidden cleanup/background work or raw-promise self-wait.
