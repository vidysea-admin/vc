## 1. Scope (in)
1. **Text chat endpoint** (threads for Pathlynks-authenticated students) and **live voice endpoint** (Gemini Live over WebSocket, D-085). **Voice transcripts persist into the same thread history as text**, so the student sees one WhatsApp-like history (D-086); audio itself is not stored [ASSUMPTION]. **Voice stays disabled for real students until A10 passes.** Voice limits (D-088 Q5, configurable per tenant): 20-minute session cap, 60 voice minutes per student per month, native audio PCM16 16 kHz in and 24 kHz out, at most 2 s of audio after a crisis trigger.
2. **Anonymous mode (text only; no public voice route exists):** public text route answers generic KB questions only, using **`GET /search`** for content and **`GET /sources`** (cacheable, no user text) only for source-kind tagging (no `/ask`, so no KB web fallback and no third-party search egress); the anonymous handler should use its own search-only KB key so "never `/ask`" is structural, not only asserted [ASSUMPTION, G4]. **VC persists no profile, transcript, thread, trace/log text or user text.** The only write allowed is one **text-free aggregate counter** (date, kind: answered | no_answer | sign_in_required | crisis, count; no text, no IP, no identifier; D-088 Q7). Personal questions return `sign_in_required`. Crisis gets the fixed message plus Tele-MANAS. Limiter: in-memory, 10 requests per minute per client. The claim is about VC storage only; provider and KnowledgeBase handling are stated separately (A15c; production basis approved in D-086 and recorded in the B13 amendment).
3. **The existing KnowledgeBase API is the RAG, used as-is (D-087).** VC calls `GET /search`, `POST /ask`, `GET /sessions/:id`, `GET /gaps`, `GET /sources` of `D:/KnowledgeBase` through `mcp/university-kb`, with a scoped key. VC keeps no copy of KB content in `D:/vc`, writes no pages and runs no page-authoring programme. Nothing in KB is changed unless a capability in section 7 truly cannot be served. No KB answer = the fixed "no sourced answer yet" text. **VC never surfaces a web answer or a weak answer:** an `/ask` answer is served ONLY when `verdict == "correct"` AND `insufficient_coverage == false` AND `web_used == false`; any other combination (including web fallback off or failed, which leaves `web_used:false`, `insufficient_coverage:true` and still a generated `answer` over weak context, `ask-v2.ts:188-219`) is the no-answer path, `no_sourced_answer` (G6). Authenticated turns call `/search` first and `/ask` only when search is insufficient (**search insufficient = 0 hits with `score` >= the configured threshold**; threshold set at U2/U6 from the recorded fixtures [ASSUMPTION]).
4. **Structured answer:** `claims[]`, each `{text, kind: number|country|fact, sourceIds[], status}` plus `sources[]` and `profileFactsUsed[]`, where `status` is `verified` | `attributed` | `unverified`. **A `sourceId` is the KB `node_id` of a `sources.internal[]` entry returned by that same turn's `/ask` call, or the `turnId` (with `sessionId`) of a `/search` hit** (G5; the KB returns no claim ids). What the KB gives: `/ask` `evidence` is optional and a **pointer only** (`sessionRef` / `sessionRefs`, no text), `sources.internal` is a flat list, and the answer is generated from node summaries, so `/ask` attribution is **answer-level, not claim-level**; the VC LLM assigns per-claim `sourceIds`, and the guard can prove only that the `node_id` was returned in this response plus the number/country match. Verification rules: (a) `/ask`: `status:verified` needs the `node_id` in this response AND a session resolved from `evidence.sessionRef(s)` (or from `/session:<id>` in the `node_id`, session-level nodes only; topic/org/year nodes need `evidence.sessionRefs`) fetched with `GET /sessions/:id` whose turn/claim text supports the claim or number; otherwise a `kind:fact` claim is `attributed` (source present, text not proven), never `verified`; (b) `/search`: `turnId`, `sessionId`, `turn.text`, `session.date` and `session.sourceId` come inline in the same hit, so no `GET /sessions/:id` call is needed and text/number checks use `turn.text`; `verified` when the claim is supported by that text. Numbers and country names are checked against the fetched/inline text (the part B2 auto-proves). Any claim without a resolvable source is dropped or returned `unverified` and shown flagged, never presented as sourced (B2). The umbrella "every sentence" claim is NOT made.
5. **Profile ranking** for authenticated students from the profile facts available (scope item 10). **Weights are configurable; the default goal is student success, the best possible outcome personalised to the student** (D-086) [ASSUMPTION: a default weight vector over fit, cost, scholarship chance and visa ease, proposed at U0 for Umesh to review, reported in the response as `rankingProfile`]. Numbers come from KB data, not the LLM (a new requirement, modelled on H2).
6. **Coverage-gap report:** authenticated-mode gap counts stored in `virtual_counsellor`, plus a country-by-theme probe of KB `/search` and KB `/gaps` (knowledge-health gaps). VC computes coverage itself, so no KB endpoint is added.
7. **Guards:** a deterministic no-quote guard keyed on a VC-side `speakers.json` (name, transliterated/Devanagari aliases and a **written-permission record**; **default-deny**: a speaker is named only when a permission record exists, D-088 Q8; external seminar speakers follow the same rule; otherwise unnamed paraphrase); **source-kind rule (D-088 Q9):** internal Vidysea seminar and TOC material may be cited as paraphrase; WhatsApp-derived material only as anonymised paraphrase, never verbatim; a claim whose source kind cannot be determined is treated as WhatsApp-derived; authenticated-student gate (Pathlynks-authenticated = consented, D-086); B1 no-drafting guard (existing `no-script`) kept.
8. **Coach first, tool-aware (D-087, Q2):** the VC coaches first (asks, structures, gives feedback on the student's own draft) and **knows every VC tool and feature and uses them to help the student**: KB answers and sources, ranking, profile view/correct/confirm, coverage and "not covered yet" answers, export/erasure, text/voice switch. A request for the VC to write an essay or SOP for the student is turned into coaching; drafting is **not** granted (B1 stays). A capability manifest skill is the single list the model is given, and a test keeps it in step with the registered tools.
9. **Crisis defaults for students with no connected counsellor (D-087, Q11):** from `qa/evidence/crisis-research-20261017/proposal.md`: a fixed safe message with Tele-MANAS 14416 (free, 24x7), asks who the student's safe adult is, **no promise of secrecy**, **keeps talking** and re-checks risk every message, never gives method information, **every flag is logged** (authenticated: who/when/level/action), and the **human-alert route is not enabled until the CEO "Nights" decision**; until then the Tele-MANAS hand-off is disclosed to the student plainly and no counsellor is promised. Unsure, indirect, Hinglish and voice cases count as the higher level. Zero liability is not achievable; this minimises exposure. Anonymous mode: fixed message plus Tele-MANAS, no record beyond the text-free counter.
10. **Profile sources (D-087, Q15), both accepted:** (a) a profile supplied by Pathlynks for the authenticated student; (b) facts extracted from the chat that **the student confirms**. Each fact carries `source: pathlynks | student-confirmed`; an unconfirmed chat-extracted fact is never used for ranking or personalisation.
11. **Limits and tenancy (D-088 Q5, Q12):** 30 requests per minute per authenticated student; 60 voice minutes per student per month; 20-minute voice session cap; all configurable per tenant. One tenant per partner plus one synthetic-data sandbox tenant that holds no real data.
12. **API surface:** OpenAPI 3, `/v1`, JWT + tenant (B21, extended with a student identity by amendment), error model, idempotent turns, profile and fact-confirmation routes.
13. **Languages:** tested for English and Hindi/Hinglish only; other languages are best effort and explicitly untested.

## 2. Non-goals
VC-owned UI/chat page/login/Hindi labels; avatar, video, booking; **ghost-writing essays or SOPs**; changing the crisis escalation recipients (human alert waits on the CEO Nights decision); application drafting; Career Library; student PII in the KB; KB content copies in `D:/vc`; a KB page store, page endpoints or page authoring; web or training-data answers; the public head-to-head "challenge" event (D-088); a Counsellor Assist roadmap (label rename only, owner Umesh); claiming pre-send enforcement for voice.

## 4. Head-to-head (release gate, D-083, D-088 Q6)
60 questions drawn from **anonymised real question logs**, >= 10 countries, 20 profile-personalised (synthetic profiles, B13), 20 Hindi/Hinglish [ASSUMPTION]. **Vidysea counsellors (Sapna ma'am's team) write the expert answers** independently and never see VC output; **two counsellors judge blind**, randomised order, accuracy, completeness, source quality, profile fit, safety (oct15_3:64-87). **Pass = VC rated equal or better on >= 60% with zero safety failures**, and A1 and A3 stay required companions (a 60% bar alone is weaker than the earlier draft). A judge must not score an answer they wrote; the counsellors are split into authors and judges [ASSUMPTION, not stated in D-088]. An LLM judge may pre-screen, never decides. The public challenge event is out of P1 scope. Human effort [ASSUMPTION estimate]: ~20 counsellor-hours to write 60 answers plus ~10 hours per judge for 2 judges.
