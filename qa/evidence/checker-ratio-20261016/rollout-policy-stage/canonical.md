# Pattern — Proportional verification

> **Type:** cross-cutting synthesis from one measured run (Pathlynks, 2026-10-05). Companions:

## TL;DR

Verification must be **intelligent, not maximal.** The checker reads the diff first, then runs only the
evidence that could change its verdict. Each extra run must answer: *"what failure could this catch that the
runs already done could not?"* If nothing, it is not run.

hai time and token burning system nhi"*. He also set the boundary: no cap on how many agents run ("cap ki
koi need nhi hai"). **The fix is to cut waste per agent, not to limit agents.**

## Research basis (STORM standard, 6 lenses, 2026-10-05; 9/13 citations independently verified)

1. **Selection plus a backstop, never selection alone.** *(High · T1)*
   - Google: presubmit runs a fast subset, postsubmit runs all affected tests.
   - Meta: predictive selection runs ~⅓ of the dependent tests and still catches >99.9% of faulty changes, because "once every few hours, all tests are exercised".
   - Microsoft TIA: falls back to all tests for any change it cannot analyse.

   → The scoped feature check plus the periodic backstop.
2. **Mutation budget:** Google's diff-based mutation testing uses about 1 mutant per changed line, capped at 7×files. Mutants on the same line virtually always share a fate. *(Medium: the PDF quotes are not independently re-verified, so this is guidance, not a floor.)*
3. **Repeats come from statistics.** *(High; the DeFlaker half is Medium.)*
   - N clean passes bound the failure rate at ≈3/N (95%, rule of three).
   - A deterministic failure needs 1 pass.
   - Varying order and process beats raising the count.
   - No source justifies 20,000-iteration loops.
4. **Reviewer inflation:** "a reviewer prompted to find gaps will usually report some, even when the work is sound" (Claude Code best practices). Scope the reviewer to correctness and stated requirements, and cap iterations (OpenHands: 3). *(High · T1)*
5. **Risk class, not review weight:** DORA found no evidence that heavier approval lowers change-fail rate, and ITIL pre-authorises low-risk standard changes. Risk follows what a change touches. *(High · T1)*

**Skeptic floor** (Cloudflare 2019, CrowdStrike 2024, Knight 2012, FB 2021, METR reward hacking):
- a fresh re-run;
- protected graders;
- config is never exempt;
- falsification is never zero;
- a backstop always exists.

```text
- BLOCKED-PROCESS (quota/usage limit, lock held by another run, external kill, infrastructure timeout) is not a FAIL: it burns no fix cycle and the unit is re-dispatched unchanged once the cause clears. Before a full suite take the project's test lock; if it is held, wait, never kill the holder.
- Kill only PIDs started and recorded by this run; never image/name-wide kills. Every manifest and verdict carries one line: `Metrics: start=<iso> end=<iso> suite_runs=<n> repeat_runs=<n> mutations=<n> cycle=<n> tokens=<n|unavailable>` (unavailable is not zero).
```

## Brief hygiene (prevents a whole wasted round)

Paste every applicable `qa/gates/` `Answered:` line into the builder brief, and add a 1-minute scope
pre-check. The incident: R-guard-asks c0 cut a prompt that grade 6-8 also uses, against the gate answer
"leave 6-7". It cost a full c1 round to undo.

## Decompose by file ownership

Units that overlap core files (orchestrator, shared prompts) become **one unit**. If a chain is unavoidable,
verify once on the merged head and skip the separate merge units.

Three rules for the Claude maker (Umesh, 2026-10-05; `maker/SKILL.md` PARALLEL WAVES point 2 and step 5):

- **Parallel by default.** Independent pieces go to parallel build subagents in one message, both inside a
  feature and across features. Serial needs a written `SERIAL:` reason.
- **One owner per overlapping file.** Merging into one unit comes first. Only when a merge is infeasible
  does the QUEUE row name `owner: <slug>`. Only the owner edits that file; the other units list it under
  `consumes:` or wait on the owner (`after:`). Example, Pathlynks 2026-10-05: the `translation_config.json`
  roadmap-block delete was folded into R-flag-cleanup, because that unit already owned the file. No second
  unit touched it.
- **No helper-level checker during a build.** Nobody dispatches a /checker for a single helper or a partial
  unit. The builder's affected tests cover that, and the independent check runs once, at the feature
  boundary, on the merged head, with its S/M/L tier taken from what the diff touches. A mid-build check
  costs a full checker spin-up (fresh context plus suite) and proves less than the feature check that
  follows.

**Evidence (Pathlynks maker session, 2026-10-05):**
- R-guard-asks and R-flag-cleanup ran in parallel worktrees, and so did the key-diff list and its checker.
  Parallel waves worked once file ownership was decided at planning time.
- An unstated gate constraint ("Leave 6-7") cost one extra fix cycle. State every applicable gate
  `Answered:` line in the brief (see Brief hygiene).
- Full-suite runs took 712-1088 s each. Repeated per-step checks multiply that number, so they dominate
  wall-clock. One check per feature on the merged head is the cheapest placement (matches maker SKILL.md step 5).

## Test-suite speed

`pytest-xdist` (`-n auto`) is an option to **measure per project**, not a default. Pathlynks has xdist 3.8.0
installed, 20 cores and no `addopts`. Risks to check before adopting:
- shared state between tests (the shared Mongo, grounding caches);
- conftest guards that assume one process;
- the baseline FAILED list must be diffed under `-n`, not assumed identical.

**Command:**
1. `pytest -m "not serial" -n auto --dist worksteal`
2. `pytest -m serial`

The marker does nothing unless the command uses it.

**Adopt only if,** across 2 runs each, the serial and parallel junit XML match on:
- collected and executed counts;
- passed, skipped, xfailed and xpassed;
- errors;
- worker crashes;
- the FAILED set.

Record the command in the project's `qa/contracts`.

### Test selection options (researched 2026-10-07)

The question was: is coverage-based selection (pytest-testmon) the way to make checks fast? The answer is **not on its own, and not first.**

| Approach | Catch rate | Fit for a laptop with many agent sessions |
|---|---|---|
| **A. Remove waste:** a `harness` marker (hook tests run only when hooks change), duration-balanced shards from stored junit durations (the pytest-split idea, no install), one full suite per machine at a time | 100%, still the full suite | **First.** On 2026-10-07, 24 of the 35 min was hook tests, plus contention from ~15 pytest processes |
| **B. Coverage-based selection** (pytest-testmon, Datadog TIA) | A 2026 study: testmon catches 86.8% of the tests that actually flip, at 41.5% precision. Instawork halved median CI time with it | **A pilot only.** It needs a full-suite backstop. Run it in shadow mode for 2 weeks and adopt it only with 0 misses. Its coverage DB is path-keyed, so `git archive` copies are unverified |
| **C. Predictive ML selection** (Meta) | 99.9% of faulty changes caught with ~33% of tests | **Skip.** It needs millions of historical runs; we have hundreds |
| **D. Batch + bisect** (bors, merge queues) | 100% at push | Already the policy-.7 step 6c. On red, bisect by unit and reopen only the culprit |

**Per-unit scope stays static:** changed files, `git grep` for removed or renamed names, and related test files. On 2026-10-07 this took ~1-2 min. The 33-67 min was never in per-unit scope: it was the full suite, the hook tests and contention, and only A fixes those.

Sources: [Impact Is Not Invalidation (arXiv 2609.25130)](https://arxiv.org/pdf/2609.25130) · [Instawork testmon](https://engineering.instawork.com/test-impact-analysis-the-secret-to-faster-pytest-runs-e44021306603) · [Meta Predictive Test Selection (arXiv 1810.05286)](https://ar5iv.arxiv.org/html/1810.05286) · [pytest-split](https://github.com/jerry-git/pytest-split) · [bors-ng](https://github.com/danielkza/bors-ng) · [Trunk batching](https://docs.trunk.io/merge-queue/optimizations/batching). These are single-search findings: the abstracts were read, the full papers were not.

## Honest limits

The cost evidence covers one day, one project and one operator. The cross-project aggregates (14 projects since ERP) are

The repeat formula and the mutant guidance come from the sources above. The risk in the other direction is real: a
checker that trims too hard misses a defect. That is why the falsification floor is never zero, why L runs a full
suite, why a budget overrun yields CONTINUE-NEEDED rather than PASS, and why the periodic backstop reopens a
feature when it finds a defect.
