# Design result: language mirroring, English KG, text model chain, streaming (D-104)

Written 2026-10-19T15:58+05:30 by p1-lang-kg-design (read-only design; no code edited). Code read at HEAD fc38e3f (only `packages/engine/src/guards/crisis.ts` differs from c8b44d0, via ISS-340). `docs/spec.md` named in the brief does not exist in the repo (docs/ holds DECISIONS.md, intent.md, plan.md, go-live-checklist.md), so spec items are cited from D-100..D-104, ARCHITECTURE.md and code comments. Nothing was measured against a live service or the database; every "today" statement is a code read, and every number is from the committed paid-run reports.

## Plain-language summary

1. Today nothing in code chooses the reply language. The model writes the answer claims in whatever language it picks (no rule in `skills/kb-answer/SKILL.md`, none in `graph.ts`). Every guard that checks the reply is English-only, and Hindi text "fails closed (unverified)" (claims.ts:551). Anonymous mode drops unverified claims, so a Hindi reply today ends as "no sourced answer".
2. Replying in the student's language therefore cannot be a prompt tweak. The safe shape: the model returns each claim twice, an English `text` that every existing guard checks and the KG/logs use, and a `localized` copy in the student's language that the student sees, checked by language-neutral guards (numbers match, no verbatim quote run, script matches, length sane). The residual risk, that a localized sentence drifts in meaning from the verified English one, cannot be closed by deterministic code; it is measured by an eval and shipped per language.
3. Biggest safety finding: the deterministic crisis guard covers English, romanised Hinglish and Devanagari Hindi only. "Any language" (D-104 item 2) means a Tamil, Bengali, Urdu or Telugu crisis message is not caught by `crisisGuard` and would be answered like an ordinary question. Needs an explicit safety decision before language mirroring is switched on (section 1, risk R1).
4. The student KG is already English by construction for chat: no model fact-extractor exists in production for chat or voice (the `extractFacts` ports in chat.ts:220 and voice.ts:221 are injected by tests only), and no per-message translation exists to remove. The unit is to build that extractor so it reads the original text and writes English `key`/`value`, with the quote kept in the original language. No data migration: no model-written chat fact can exist in production yet.
5. A text provider chain exists (`FailoverProvider`, providers/src/index.ts:744) but it is LiteLLM-only: Ollama is not in `createProvider`, Ollama errors are not on the retryable whitelist (index.ts:621-629) so an Ollama failure would never fail over, and the Gemini text provider is a stub that throws `ProviderNotWiredError` (index.ts:356-381). Chain work is a provider unit, not a config change.
6. The committed paid runs say the order matters: model-hop latency (non-streamed, 20 samples) was GLM p50 5.35 s / p95 9.31 s (FAIL against 3 s), DeepSeek p50 1.23 s / p95 2.67 s (PASS). Streamed first-token time for either was never measured. Measure it first; if GLM stays slow, GLM-first with a 3 s first-token timeout fails over to DeepSeek on a large share of turns and A8 still fails. Order is Umesh's call (D-104 item 3); the data argues for DeepSeek first or a hedged start.
7. No streaming exists anywhere on the HTTP path: `ApiResponse.body` is one string (server.ts:112-116) written with `res.end` (server.ts:901-902). Streaming needs a transport change plus a client change in Pathlynks. Guarding a stream: buffer-then-release per claim, never stream-then-retract.
8. Non-English retrieval is not implemented: the graph sends the raw student text to `searchKb` (graph.ts:608). The A2b "query rewrite to English" exists only as an eval-harness prompt (run-kb.ts:30), and A2b is NOT PROVEN (0/15 on a frozen fixture). Mirroring the reply in Hindi is of little use if the KB search for a Hindi question returns nothing. Needs a small query-rewrite call, only for non-English turns, nothing stored.
9. Build plan: 11 units, three parallel lanes (providers, KG, language) and a serial tail (streaming engine, transport, paid eval). Sizes and acceptance below. Five decisions for Umesh at the end.
10. Hard rule kept: `crisisGuard` runs on the original text first, before any model call, and a crisis turn makes no model call, so a provider outage never hides a crisis.

## 1. Reply language today, and what changes

### Evidence (today)
- Reply text comes from `answerFromKb` (graph.ts:599-689): `provider.generate({skillName: "kb-answer", ... input: {question: input.text, evidence, priorFlag}})` (graph.ts:643-648), then `message = shown claims joined with " "` (graph.ts:667). The language is whatever the model writes. `skills/kb-answer/SKILL.md` has no language rule; the evidence is English KB text.
- Guards are English-only: `supports()` (claims.ts:551-571) fails closed on Hindi; `CRISIS_FORBIDDEN_PATTERNS` (graph.ts:99-109), `noScriptGuard`, `numberMentions`/`countriesIn` and `STRESS_CHECK_IN` are English. The "(unverified)" suffix (graph.ts:667) and every fixed text (graph.ts:70-134: no-answer, apology, sign-in, helpline, crisis, coach fallback, tool messages) are English; the crisis core carries one Hindi gloss in brackets (graph.ts:86).
- Rule-based classifiers `classifyQuestion` / `classifyIntent` are tested for English and Hindi/Hinglish only (classify.ts:14); unknown languages fail closed to "personal" (anonymous: `sign_in_required`) or fall to `search_kb`.
- Language detection exists in two copies: `isDevanagari(text) ? "hi" : "en"` at graph.ts:394/522 and `/[ऀ-ॿ]/.test(text) ? "hi" : "en"` at voice.ts:849. Both feed the escalation record's `lang`. Chat and voice never translate: `translatedText: input.text` (graph.ts:522, voice.ts:849), so the escalation classifier already reads the original. Nothing to remove for D-104 item 1 on these paths.
- `crisisGuard` (crisis.ts:895) matches English, romanised Hinglish and Devanagari (ISS-340, commit 4df25b8). A grep for Tamil, Bengali, Telugu, Marathi, Gujarati, Urdu, Punjabi, Kannada, Malayalam finds no pattern. Marathi shares the Devanagari script but not the words.
- Voice: Gemini Live chooses its own spoken language; `systemInstruction` is optional config (voice.ts:217, 909; live.ts:814) with no language rule. The crisis voice message is pre-rendered PCM (voice.ts:211 `crisis: { message }` in deps; live.ts), one language.

### Design
**A. Detect (deterministic, before any model, cheap).** One function `detectLanguage(text) -> { script, lang, confidence }` replacing both `isDevanagari` copies:
- Script by Unicode block: Latin, Devanagari, Bengali, Gurmukhi, Gujarati, Odia, Tamil, Telugu, Kannada, Malayalam, Arabic (Urdu), others.
- Latin-script Hinglish: reuse the Hinglish marker lists already in classify.ts (PERSONAL_HINGLISH, QUESTION_HINGLISH, ADVICE_HINGLISH) and the romanised crisis vocabulary; a Latin turn with 2+ Hinglish markers is `hi-Latn`. Everything else Latin is `en` (or "other-latin" if the model says otherwise later).
- Mixed script: majority script of letters wins; the model refines it in the answer call (`replyLang` output), but the deterministic result is what the crisis path and fixed texts use, so no model is needed for the crisis message.
- Used by: crisis message choice, fixed-text catalog choice, escalation `lang`, `chat_turns.lang`, telemetry.

**B. Mirror (answer call).** `kb-answer` SKILL.md gets a language rule: "Reply in the language and script of the student's latest message. Latin-script Hinglish gets Latin-script Hinglish; Devanagari gets Devanagari; code-mixed gets the dominant one. Claims are written twice." Output schema change (graph.ts:356-361):
`{ replyLang, claims: [{ text (English), localized (replyLang), kind, sourceIds }], followUp?, followUpLocalized? }`.
- English `text` goes through the unchanged chain: `guardClaims` (claims.ts:593), source-kind rules, no-quote guard, restricted-text check. It is also what is stored and logged, so the audit trail stays English and checkable.
- `localized` is what the student sees and is shown only if the English claim survived, plus language-neutral checks: (i) number parity, every digit run in `text` appears in `localized` after normalising digit systems (Devanagari/Arabic-Indic to ASCII) and spelled-out Hindi figures covered by `numberMentions`; (ii) `hasVerbatimRun(localized, restrictedText)` for every restricted text (language-agnostic n-gram check, as at claims.ts:676 and graph.ts:669); (iii) script of `localized` equals the detected script (or its Latin twin for hi-Latn); (iv) length ratio localized/English within [0.4, 3.0]; (v) no URL/phone/email not in the English text. Any failure drops back to the English claim text for that claim (a student sees English rather than a wrong sentence) and counts `localized_guard_fail` (text-free).
- Residual risk R2: meaning drift between `text` and `localized` is not checkable by code. Controls: ship per language behind an allow-list (`VC_REPLY_LANGS`, start hi, hi-Latn, en, then add), an eval with a native-speaker-rated synthetic set per language before a language is added, and the counter above. "Any language" in D-104 is the end state; the allow-list is the rollout lever.
- Fixed texts: a typed catalog `FIXED_TEXTS[lang]` for every constant at graph.ts:70-134 plus STRESS_CHECK_IN and the "(unverified)" suffix, English fallback for any language not in the catalog. Human-vetted wording only (not generated at runtime).

**C. Crisis message in the student's language.** `CRISIS_MESSAGES: Record<lang, { student, anonymous }>` holding vetted translations. For a detected language with a vetted entry, send it. For any other language, send the existing English text plus the Hindi gloss, i.e. English+Hindi as D-104 specifies (graph.ts:83-96 already has that shape). Rules: (1) the table is hand-vetted by Umesh or the clinical/legal reviewer, never model-generated; (2) every entry must pass `CRISIS_FORBIDDEN_PATTERNS` equivalents (the English regexes cannot test other scripts, so each vetted entry ships with a fixture asserting the helpline number 14416, the "not a counsellor / no counsellor being connected" statement and the safe-adult question, by exact-substring checks); (3) voice: pre-rendered PCM per vetted language (live.ts crisis message), other languages keep the current audio. Changes the B24.7/A11b fixed text, so the contract owner (orchestrator) must amend `qa/contracts` first; I did not edit it.

**D. Retrieval for non-English turns.** Add a runtime query-rewrite: only when `detectLanguage` says non-English, one short provider call (`skill: kb-query-rewrite`, output `{ query }`, max ~64 tokens) produces an English search query; `searchKb(query)` replaces `searchKb(input.text)` at graph.ts:608. Nothing from it is stored or shown; it is a retrieval aid, not a translation of the message, so it does not contradict D-104 item 1 (Umesh to confirm, decision Q2). Cost: one extra short hop before the first claim; budget it inside the 3 s first-token bound (section 4).

### Risks specific to this item
- R1 (high, safety): uncovered-language crisis messages. Proposal, in order of cost: (a) for any turn whose script is not Latin or Devanagari, or whose language is not in the vetted-pattern set, run the existing `concern-classifier` skill (engine/guards/concern-classifier.ts) as a fail-closed safety screen in parallel with the answer call; the first released chunk waits for its verdict; "possible" or error means the fixed crisis message; (b) always append the localized or English+Hindi helpline line to replies in uncovered languages (anonymous mode already does this for non-answers, graph.ts:80-81); (c) a follow-up unit with native-speaker-vetted recall patterns for Tamil, Telugu, Bengali, Marathi, Gujarati, Kannada, Malayalam, Punjabi, Urdu (same recall-only style as ISS-340). (a)+(b) are in unit LK5; (c) is a separate backlog item that needs human vetting. Umesh decides whether "any language" ships before (c) (decision Q1).
- R3: with more languages the rule classifiers fail closed to "personal" for anonymous users (classify.ts); anonymous non-Hindi users mostly get sign-in prompts until classifier coverage grows. Accept and report.
- R4: model transcription of non-English quotes (section 2) can drop facts; measured in eval.

## 2. Student KG: where facts are written, in what language, and the design

### Evidence (today)
- Chat/voice proposed facts: `FactExtractor` port (chat.ts:176-183), called after the turn is stored (chat.ts:705-715), values redacted and written by `proposeProfileFact` (packages/db/src/profile-facts.ts:62-95; `ProfileFactDoc` has `key`, `value` (redacted string), `status`, `source: "chat"`, `threadId`, `turnId`, no language, no quote). Max 5 per turn (chat.ts:128). Voice does the same (voice.ts:720-740). `grep` for implementations finds none: only the optional deps in apps/api/src/index.ts:173 and tests. So in production no model currently extracts chat facts, and no language question exists in stored chat facts.
- Counsellor scribe (post-session): `extractFacts` (scribe/nodes.ts:1176-1216) with `skills/fact-extraction/SKILL.md`. The skill reads the "English-translated text" (SKILL.md line 15); `TranscriptTurnSchema` requires `translatedText: z.string()` (schemas.ts:162) supplied by the caller. Each fact must cite a quote that is a verbatim substring of `text` or `translatedText` (nodes.ts:1050-1100; `locateCitation`). Auto-verify templates are English-only and bind to the original `text` (nodes.ts:780-803): a non-English quote returns `unrecognised-form` and `needsReview: true`, i.e. fails toward counsellor review. Stored turn docs keep both texts (db collections.ts:124-143).
- Chat stored text is redacted (names, phones, emails) before write (chat.ts:631-636, D-093 6A); `translatedText` is not stored for chat.

### Design
- Original message: stored as written (redacted per D-093 6A, unchanged). Add `lang` (detected, section 1A) to the user row of `chat_turns` and `replyLang` to the assistant row.
- Extraction: one call after the reply is released, off the latency path, reading the ORIGINAL text and writing English `key` and `value` directly. No translate step. Implementation = reuse, not new skill: edit `skills/fact-extraction/SKILL.md` in place (rule: read `text`; `translatedText` is optional hint, may be empty; write `key` as an English snake_case slug from the existing vocabulary and `value` in English; `source.quote` copied verbatim from `text` in its original script) and add a thin adapter that calls scribe `extractFacts` with a single student turn `{turnId, speaker: "student", lang, text, translatedText: ""}` and maps `Fact` to `{key, value: String(value)}`. Adapter lives next to `extractFacts` in scribe/nodes.ts and is wired as the default `extractFacts` in apps/api/src/index.ts (chat setup, line 173/411) and voice. `translatedText: ""` is valid under the current schema (`z.string()`), so no schema change in the scribe path; a test must confirm `locateCitation` and the escalation guards (guards/escalation.ts:189-192) treat an empty `translatedText` safely.
- Schema impact (db, additive, optional fields only): `ProfileFactDoc.sourceLang?: string`, `ProfileFactDoc.quote?: string` (verbatim original-language snippet, redacted like `value`; satisfies "every fact carries a source", ARCHITECTURE.md section 5), `chat_turns.lang?`, `chat_turns.replyLang?`. `profile_facts` `value` stays English by definition; add no `valueLang` field.
- Prompt change: above. Add examples with a Devanagari and a Hinglish turn.
- Citation guard consequence: B2 stays strict. A model that mis-copies a Devanagari quote makes the fact drop (`dropped` list), never fabricates. Eval metric: fact survival rate on a synthetic multi-language set; target set at design review, I suggest at least 80 percent of facts a native rater marks as present survive for hi, hi-Latn, en.
- Non-English facts need counsellor review (auto-verify is English-template only). Acceptable: P1 already requires counsellor approval for everything entering the student model (ARCHITECTURE.md section 5).
- Migration of existing non-English facts: none required. Evidence: no chat/voice extractor in production, so `profile_facts` holds no model-written rows; scribe `facts` are written from `translatedText` already (English values). I did not query MongoDB. To confirm before go-live, a read-only audit script (proposal only, not run here) counts `profile_facts` and `facts` rows whose `value` has a non-Latin letter; if any exist, a proposal file (not a write) lists them for re-extraction through the same adapter. Production writes stay behind the human gate.
- Privacy: the extractor receives the live, unredacted turn (chat.ts:707) and sends it to the model provider. With Ollama or Gemini this makes them a processor of real student text (D-104 Result). The chain must stay disabled for real student text until the consent/legal team's processor register covers it (B13, owned by them per D-103). Design: a deployment flag `VC_TEXT_CHAIN_REAL_STUDENTS` (default off) that is checked at provider construction and refuses non-synthetic tenants, mirroring the sandbox `syn-` rule (chat.ts:760). Hard boundary preserved.

## 3. Model chain

### Evidence (today)
- One provider per process: `createProvider(loadProviderConfig(env))` (apps/api/src/index.ts:262), shared by chat, anonymous and the classifier path (index.ts:267-268, 289, 406). `ProviderConfigSchema` knows mock, gemini, litellm, rules (providers/src/index.ts:113-142); Ollama is explicitly "NOT part of the production failover chain or createProvider", reachable only through eval runners via `VC_REAL_MODEL=ollama:<id>` (index.ts:1020-1027, 1231-1238).
- Failover exists: `FailoverProvider` (index.ts:744-904) cycles `chain[attempt % chain.length]` (wraps around), total budget 10 attempts and 45 s deadline by default, aborts the losing attempt, full-jitter backoff, alert plus `AiUnavailableError` on exhaustion, never drops to rules.
- Retryable whitelist `isRetryableProviderError` (index.ts:621-629): LiteLlm timeout/malformed/network, HTTP 429 or >=500, `ModelOutputSchemaError`. `OllamaTimeoutError`, `OllamaHttpError`, `OllamaMalformedResponseError`, `OllamaNetworkError` (index.ts:1057-1095) are not on it, so a chain containing `OllamaProvider` would throw on the first Ollama failure instead of failing over. A malformed GLM reply (the one seen in the paid run) is an `OllamaMalformedResponseError` when the body or `message.content` is not JSON, or a `ModelOutputSchemaError` when JSON is the wrong shape; only the latter is retryable today.
- Gemini text: `GeminiProvider.generate` throws `ProviderNotWiredError` after the authorization check (index.ts:373-376). Live voice is a separate seam (`LiveProvider`, live.ts) and is unaffected.
- Spend control exists only in the eval harness: `packages/engine/evals/budget.ts` (JSONL ledger, USD 50 per run, 200 per month, reservation before request). Actual-token capture (`prompt_eval_count`, `eval_count`) exists only on branch `p1/ollama-tokens` (commit 18da02d, merged into neither this checkout's providers/src/index.ts nor main as far as this tree shows: grep for `prompt_eval_count` in packages/ and apps/ finds nothing). Runtime student turns have no per-call token or cost record; `recordStudentUsage` (db chat-threads.ts:471-506) only counts `textTurns` and `voiceMs`.
- Paid-run evidence (committed reports): `qa/evals/p1/real-20261019-glm/latency-report.md` (cc14c37): 20 samples, first-token recorded equal to full answer (not streamed), p50 5355 ms, p95 9310 ms, FAIL vs 3000. `real-20261019-deepseek/latency-report.md` (1a1ee67): p50 1229 ms, p95 2674 ms, PASS. Both reports print the same spend figure (USD 0.172089), which suggests the figure is the pre-request reservation, not actual spend; D-103 item 4 already says Ollama USD is notional.

### Which calls move to the chain
Student-surface text calls: (1) `kb-query-rewrite` (new, section 1D), (2) `kb-answer`, (3) coach (graph.ts:697), (4) fact extraction (section 2). Kept where they are: Gemini Live voice; the concern classifier and the counsellor scribe/cards (separate configs via `concernClassifierProviderConfig`, index.ts:268) unless Umesh widens D-104 (decision Q4). Reason: the classifier is safety-relevant and the chain has no safety evaluation yet.

### Chain design
`VC_TEXT_CHAIN="ollama:glm-5.3-flash,ollama:deepseek-v4.1-flash"` (later append `gemini:flash-lite`), parsed by `loadProviderConfig` into a new `chain` config; `createProvider` builds `OllamaProvider` per entry (price from the existing table, index.ts:1051-1055) and a `FailoverProvider` over them.
- Failover triggers (per hop): first-token timeout (not total timeout) of a stated value, a total attempt timeout, HTTP 429 and >=500, network error, empty content, malformed JSON, schema-invalid output (all except the last = go next). Not failover: HTTP 400/401/403/404 (config or auth, per D-020), a budget stop, `ProviderAuthorizationRefusedError`, a caller abort.
- Chain semantics for chat: single pass (one attempt per hop, no wrap-around), `maxAttempts = chain.length`, wall-clock deadline sized to the product bound (suggest 12 s) instead of 45 s, so the student never waits through a second lap. Needs a constructor option; the existing default stays for other callers.
- Streaming rule (section 4): failover is allowed only before the first chunk is released to the client; after that a hop failure ends the stream (no splicing two models' answers).
- Ordering risk R5: GLM first with a 3 s first-token timeout would time out on a large part of turns given its non-streamed p50 of 5.35 s; each timeout costs 3 s before DeepSeek even starts, so A8 first-token would fail. Do not decide on non-streamed numbers: the first deliverable of the lane is a streamed TTFT probe of both models. If GLM streamed TTFT p95 is above about 1.5 s, recommend DeepSeek first, or hedging (start hop 2 after 1.2 s if no token, cancel the loser).
- Budget and ledger per hop: new text-free `llm_usage` collection in `virtual_counsellor`, one document per tenant per UTC day per model id (model ids contain dots, so they are values, not field names): `{tenantId, day, model, calls, failovers, inTokens, outTokens, unreportedCalls, notionalUsd}`, `$inc` only. Tokens come from the provider's `afterResponse` hook using `prompt_eval_count`/`eval_count` (needs the p1/ollama-tokens branch merged first); missing or invalid counts increment `unreportedCalls` and keep the reservation estimate, never zero. A daily notional cap per tenant (`VC_TEXT_DAILY_CAP_USD`, notional) stops new chains with the apology, same as A12. No text and no student id in this collection. Per-hop failover reason is logged text-free.
- Gemini Flash-Lite later: needs a real Gemini text adapter (the stub today). Separate unit, held until Umesh supplies the model id and approves the key use; the chain config then gains one more entry.

## 4. Streaming

### Evidence (today)
- No streaming on HTTP: `ApiResponse = {status, headers, body: string}` (server.ts:112-116); the node adapter does `res.writeHead` then `res.end(out.body)` (server.ts:891-903); `respond()` JSON-stringifies (server.ts:597). The only streaming in the repo is the voice WebSocket (voice.ts, live.ts). apps/web is the counsellor reference UI and has no student chat client (no EventSource or reader use); Pathlynks is the client.
- Providers are not streamed: Ollama sends `stream: false, format: "json"` (index.ts:1167-1173); LiteLLM has no streaming; the A8 eval records first token equal to full answer (run-latency.ts doc comment) and has `hooks.firstToken()` ready for a real value (latency.ts:53-60). A8 bounds: first token p95 <= 3000 ms, full p95 <= 10000 ms, at least 20 samples (latency.ts:6-8).
- The reply is JSON `claims` that are verified after generation, in two passes against turn-wide restricted material (claims.ts:593-697), and then joined and re-checked as one message (graph.ts:653-672). That is why a plain token stream cannot go to the student as it is.
- LangGraph: `@langchain/langgraph` 1.4.17 installed; `streamMode` includes `"custom"` and nodes receive a `writer` in config (verified in node_modules/@langchain/langgraph/dist/pregel/types.d.ts lines 19, 73-100 and runnable_types.d.ts line 43). Brain page `concepts/langgraph/streaming.md`: `messages` mode only sees LangChain chat-model tokens; our providers are not LangChain models, so use `custom` events emitted by the answer node. (brain consult logged, id af2b040adc9c.)

### Design
**Principle: nothing reaches the student that the guards have not passed; no retraction.** "Stream then retract" is rejected: a retracted sentence has already been read, and this is a student safety surface. Buffer-then-release at claim granularity:

1. Order of events for a turn (unchanged first steps): HTTP request in, body cap and `crisisGuard` on the full original text (chat.ts:556-561, anonymous.ts:426) before any model call. A crisis turn returns the fixed message as a single `done` frame; no model call, no stream.
2. Prefetch: all KB search hits and, on the authenticated `/ask` path, all `get_session` turns are fetched before generation, so the turn-wide restricted-text set is complete before the first claim can be released (today pass 1 grows it claim by claim, claims.ts:630-640).
3. Provider stream: change the answer output from one JSON object to claim-per-line JSON (one claim object per line, final line `{"followUp": ...}`), parsed incrementally; each complete line is Zod-validated alone. A malformed line drops that claim (fail closed); a malformed first line before any release triggers failover.
4. Per completed claim: run pass 1 and pass 2 of `guardClaims` for that claim, the localized checks (section 1B), the prior-flag forbidden patterns, the redaction and `noQuoteGuard`, and a verbatim-run check against a sliding window of the last 7 released words plus the new claim (cross-boundary runs). Pass: emit `claim` event `{index, text: localized or English, status}`. Fail: skip, emit nothing.
5. Authenticated unverified claims are emitted with the "(unverified)" suffix (graph.ts:667). Anonymous never emits unverified claims (graph.ts:662).
6. End: if nothing was emitted, send the fixed no-answer as the only chunk (and the gap or counter write, as today). Then `finish` effects as one last chunk: stress check-in or prior-flag helpline suffix (graph.ts:453-468). Then the `done` frame carries the full canonical `TurnResponse` (message, claims, sources, state). The client treats `done` as authoritative; the streamed text is, by construction, a prefix-equal rendering of `done.message`, so nothing is ever contradicted.
7. Persistence after completion only: lease claimed before the model call as today (chat.ts:631), `completeChatTurn` after `done` (chat.ts:704), then fact extraction (off the latency path). A client disconnect aborts the model call through the existing signal path (providers/src/index.ts:71 `signal`) and abandons the lease (chat.ts:649-651).
8. Mid-stream provider failure after the first release: no splice. Emit `done {state:"ok", retryable:true, truncated:true}` with the helpline-free partial text already shown, abandon the lease (nothing stored, as A12), retry re-runs with the same `clientTurnId`. Umesh to confirm this partial-answer behaviour (decision Q5).
9. Idempotent replay (chat.ts:638-642) returns the stored response as a single `done` frame.

**Transport.** Opt-in per request: `Accept: text/event-stream` on the existing turn routes (authenticated: chat.ts postChatTurn; anonymous: ANONYMOUS_PATH). Default stays JSON, so the current contract and every test keep working. Add an `ApiResponse.stream?: AsyncIterable<string>` variant; the node adapter (server.ts:891-906) writes SSE frames with `content-type: text/event-stream`, `cache-control: no-store`, `x-accel-buffering: no`, flushes each frame, and ends on `done`; error before the first frame stays a normal JSON status. Events: `meta` (turnId, replyLang), `claim`, `done`, `error`. Update `openapi.ts` and its route-list test (CHAT_ROUTES equality test). Rate limit, body cap and auth run before the stream opens, unchanged.

**Engine path.** One code path: `answerFromKb` gets an optional emitter (LangGraph `config.writer`, stream mode `custom`); with no emitter it behaves exactly as today, so the non-streamed and streamed results share the same guards and tests. New helper `runStudentTurnStream(deps, raw)` wraps `compiledGraph.stream({raw}, {streamMode: ["custom", "values"]})`.

**A8 as first token.** Define first token = first released guarded `claim` event, measured server-side (request received to first frame written) and in the harness (`hooks.firstToken()` at the first `claim` event). Time budget for p95 3 s: crisis scan and routing (ms), KB search plus prefetch, optional query-rewrite hop, model TTFT plus time to the end of the first complete claim line, guard (ms). The rewrite hop and "first complete claim" (not first token) are the cost of buffer-then-release; this is the honest number and the contract text (A8) must be amended to say "first released claim" (contract owner). Full-answer bound 10 s unchanged.

**Risks.** R6: the first complete claim arrives later than the first raw token (a claim is a sentence); measure, and prompt the model for a short first claim. R7: proxy buffering in front of the API (needs `x-accel-buffering: no` and deployment check). R8: a client that does not support SSE keeps the JSON path (no regression).
