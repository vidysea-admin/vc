## Secrets and crypto
- **[VA1]. Secrets never in committed files, responses, logs or traces.** (serves: intent#1, intent#3) criticality C
  - `config/sources.json` holds non-secret fields and `*Ref` env NAMES only; `.env.example` holds key names with empty values; no tracked file holds a password, token, JWT secret, master key or connection string with credentials.
  - No admin route response, audit_log row, log line or error message contains a stored secret, a password hash, a raw API key (other than the once-shown create/rotate response), or the master key.
  - **verify (static):** `git -C D:/vc grep -nIE "(password|passwd|secret|token|master_?key)[\"']?[[:space:]]*[:=][[:space:]]*[\"'][^\"'$<{][^\"']{5,}" -- config .env.example apps/api/src packages/db/src mcp/pathlynks packages/schemas/src` returns no line that is a real secret value (test fixtures under `tests/` are excluded and must use obvious dummies such as `test-secret-not-real`); `git grep -nIE "postgres(ql)?://[^[:space:]\"']+:[^@[:space:]\"']+@"` over tracked non-test files returns nothing; `git ls-files | grep -E "(^|/)\.env($|\.)" | grep -v "\.env\.example$"` returns nothing. The scan is pattern-based; no secret value is ever quoted into a command, manifest or verdict.
  - **verify (route test):** `apps/api/tests/admin-secrets-leak.test.ts`: seed a source with a known dummy secret via `PUT /admin/api/sources/:id/secret`, a known dummy password for an admin, then call every GET route and every error path as super-admin and as viewer and assert that the dummy secret, the dummy password, the stored `secretEnc` fields (`iv`, `tag`, `ct`), `passwordHash` and `VC_ADMIN_MASTER_KEY` / `VC_ADMIN_JWT_SECRET` values appear in no response body, no captured log line (console / logger spy) and no audit_log row. `hasSecret: boolean` is the only secret signal returned. A created or rotated key appears exactly once (in that response) and a following `GET sites` shows only `keyPrefix`.
- **[VA2]. AES-256-GCM round trip and tamper rejection.** (serves: intent#3) criticality C
  - `encryptSecret(plain, key32)` returns `{iv, tag, ct}` with a fresh random 12-byte iv per call (two encryptions of the same plaintext differ); `decryptSecret(enc, key32)` returns the plaintext.
  - A flipped bit in `ct`, `tag` or `iv`, a truncated tag, and a wrong key all throw; none returns a plaintext. A master key that is not base64 of exactly 32 bytes is refused at startup / construction.
  - Stored secrets are written only through `sources.setSecret` and only as the encrypted triple (never plaintext in Mongo).
  - **verify:** `cd D:/vc/packages/db && pnpm exec tsx --test tests/admin-store.test.ts` (cases: round trip, iv uniqueness over 50 calls, tamper of each of ct/tag/iv, wrong key, bad master-key length, fake-Db document after `setSecret` contains no plaintext substring).
- **[VA3]. Config schema rejects secret values.** (serves: intent#3) criticality C
  - `SourceConfig` / `SourcesFile` are `.strict()` as in spec S1; `loadSourcesFile(path)` returns the seeded file (four Pathlynks GitHub branches + the Pathlynks Postgres, `tables` non-empty, `sslmode` require or verify-full).
  - `loadSourcesFile` throws on: an unknown key; a field named `password` / `secret` / `token` (any case) holding a value; a `passwordRef` / `tokenRef` that is not an env-name shape (`^[A-Z][A-Z0-9_]*$`); a connection string with embedded credentials; a Postgres source with `sslmode` outside the enum.
  - **verify:** `cd D:/vc/packages/schemas && pnpm exec tsx --test tests/sources.test.ts` (one test per rejection above; one test parses the real `config/sources.json`; one asserts `.env.example` contains every `*Ref` name found in `config/sources.json` with an empty value).

## Admin auth, roles, audit
- **[VA4]. Admin login, JWT typ check, rate limit.** (serves: intent#1) criticality C
  - Passwords: scrypt (N=2^15, r=8, p=1, 16-byte salt), constant-time compare; wrong password and unknown email return the same generic 401 body and status.
  - `POST /admin/api/login` returns an HS256 JWT signed with `VC_ADMIN_JWT_SECRET`, lifetime 8 h, claims `{sub, role, typ:"vc-admin"}`.
  - A token without `typ:"vc-admin"` is refused (401) on every `/admin/api/*` route, including a valid voice ticket minted by `mintVoiceToken` / `mintAnonymousVoiceToken` and a student or counsellor JWT. An expired token, a token with `alg:none`, a token signed with another secret, and a disabled user's token are refused.
  - Login is limited to 5 per minute per IP: the 6th attempt in the window gets 429 with `Retry-After`, including when the attempts used different emails; a correct password does not bypass the limit once it is hit. The limiter key is the nginx `X-Real-IP` client key as for the other routes.
  - `pnpm -C apps/api admin create <email> --role super-admin` reads the password from a TTY prompt; it refuses a password given on argv and never echoes it.
  - **verify:** `cd D:/vc/apps/api && pnpm exec tsx --test tests/admin-auth.test.ts` (cases above, with an injectable clock for expiry and the limiter window; CLI test asserts argv password refusal and that stdout/stderr never contain the typed password); `pnpm -C apps/api typecheck`.
- **[VA5]. Role matrix.** (serves: intent#1) criticality C
  - viewer: GET only. admin: everything except `admins` routes and `PUT sources/:id/secret`. super-admin: all.
  - For every non-GET route in spec S3 (`POST admins`, `POST sites`, `PATCH sites/:id`, `POST sites/:id/keys/rotate`, `POST sites/:id/revoke`, `POST sites/:id/unrevoke`, `POST sources`, `PUT sources/:id/secret`, `POST sources/:id/test`, `POST sources/:id/sync`): viewer gets 403 with no side effect on the fake Db; admin gets 403 on `admins` and `secret`; super-admin succeeds. A request with no token gets 401, never 403/200.
  - A viewer or admin cannot grant themselves a higher role (`POST admins` / role change by a non-super-admin is 403; a body `role` on a self-targeted call is ignored or refused).
  - **verify:** `cd D:/vc/apps/api && pnpm exec tsx --test tests/admin-routes.test.ts` (table-driven: route x role -> expected status, plus a fake-Db write-count assertion for every 403). The checker also diffs the table's route list against the S3 route list in the spec; a route in `admin-routes.ts` missing from the table is a FAIL.
- **[VA6]. Audit row per write.** (serves: intent#1) criticality C
  - Every non-GET admin route writes exactly one `audit_log` row `{at, actorId, action, target, ok}` with `ok:true` on success and `ok:false` on a refused or failed write (403, validation error, downstream error), including login attempts (success and failure) and role-denied calls. GET routes write none.
  - `audit_log` is append-only: the store exposes no update/delete; the row contains no secret, no password, no raw key, no request body.
  - `GET /admin/api/audit` returns rows newest first, role viewer allowed.
  - **verify:** `apps/api/tests/admin-routes.test.ts` (audit count delta per route x outcome) and `cd D:/vc/packages/db && pnpm exec tsx --test tests/admin-store.test.ts` (no mutating method on `audit`; append stamps `at` from the clock).
- **[VA7]. Partner key reuse, no second key system.** (serves: intent#2) criticality H
  - Sites map to the existing `partners` collection. Create site = `addPartner`, rotate = `rotatePartner` (scope pub or srv), revoke = `revokePartner`, list = `listPartners`, plus the new `updatePartner` (name, allowedOrigins via `normalizeOrigin`) and `unrevokePartner`, all in `apps/api/src/partners.ts` and all taking the same `PartnerStore`, pepper, `reservedIds` and `ownTenants` as the CLI.
  - No new key-hash, key-format or key-lookup code path exists: the key format stays `vck_(pub|srv)_<partnerId>_<43-char base64url>` and `createPartnerRegistry.authenticate` is the only verifier. A key created in the console authenticates on `POST /v1/public/chat/turns` (pub) and on the student routes (srv) through the existing registry, and a revoked or rotated-out key gets the uniform 401 there within the 60 s cache bound (test uses the injectable cache TTL / clock).
  - Reserved ids, invalid origins (path, wildcard, non-https) and a duplicate id are refused by the console exactly as by the CLI. The CLI (`pnpm -C apps/api partner ...`) and its existing tests still pass unchanged.
  - **verify:** `apps/api/tests/admin-routes.test.ts` (console-created key then `createPartnerRegistry.authenticate`; update/unrevoke cases; reserved-id and origin refusals); `cd D:/vc/apps/api && pnpm exec tsx --test tests/partners.test.ts` stays green (74 tests at baseline, none removed or weakened); static: `git -C D:/vc grep -nE "createHmac|timingSafeEqual" -- apps/api/src/admin-routes.ts apps/api/src/admin-auth.ts` shows hashing only for the admin password (scrypt) and JWT, none for partner keys.

## Pathlynks read tools
- **[VA12]. Pathlynks student scoping, fail-closed write privilege, timeout and row cap.** (serves: intent#5) criticality C
  - `createPathlynksPort(...)` exposes only `getStudentProfile`, `getSavedCareers`, `getCompareList`, `getAssessmentStatus`. Every query is parameterised (`$1`), SELECT only, and contains `WHERE student_id = $1` bound to the verified student id; no string concatenation of an id, table or column into SQL; the table names come from the `config/sources.json` allow-list.
  - The student id comes only from the verified auth context passed by the engine, never from tool arguments or message text: a tool call carrying another student's id in its arguments, or a prompt-injection attempt in the user text, still queries the verified id (or is refused).
  - Each connection sets `statement_timeout=3000`; results are capped at 50 rows (a fake returning 500 rows yields 50, flagged truncated). A connection or query timeout/error returns a typed "unavailable" result, never throws into the turn and never leaks the connection string or password.
  - On connect the port runs `has_table_privilege(current_user, <table>, 'INSERT')` (and UPDATE/DELETE) for every configured table; if any is true the port refuses to serve (fails closed) and records that the privilege check failed; a privilege-check error also fails closed. No code path issues INSERT/UPDATE/DELETE/DDL; a test asserts that every SQL string issued by the port starts with `SELECT` or is the privilege/`SET` probe.
  - **verify:** `cd D:/vc/mcp/pathlynks && pnpm exec tsx --test tests/*.test.ts` using a fake `pg` client that records `text`/`values` (assert parameterisation, `student_id` binding, timeout setting, row cap, privilege refusal for each of INSERT/UPDATE/DELETE true, privilege-check error, SQL allow-list regexp over all captured statements); `pnpm -C mcp/pathlynks typecheck`. **Live connection: see [VA20] (HELD on G1/G2).**

  - **verify:** `cd D:/vc/packages/engine && pnpm exec tsx --test tests/pathlynks-tools.test.ts` and `cd D:/vc/apps/api && pnpm exec tsx --test tests/chat-pathlynks.test.ts` (two-student fake port, anonymous-route refusal, unavailable path, injection text in the user message).

- PROPOSED-ISSUE spec S3 "rate-limited 5/min/IP" (spec user-types table) vs "Login rate limit 5/min/IP": whether the 6th attempt or a success counts toward the limit, and whether the limiter state is in memory (lost on restart, per-process) or in Mongo.
