PROPOSED-ISSUE lines (none is a fail; nothing written to the ledger):
- PROPOSED-ISSUE P2: residual by design, already stated in the manifest. The crisis scan is synchronous (it blocks the Node event loop for tens of ms per 64 KiB request) and is unlimited per client by B24.7. A client looping on large in-cap bodies can still use most of one process's CPU (roughly 20 to 70 requests per second of 64 KiB at 15-50 ms each saturates it). The cap bounds it about 4x; a per-client crisis budget or a worker thread would be the next step and needs Umesh (it changes B24.7).
- PROPOSED-ISSUE P3: when a client keeps uploading after the server has answered 413 (or a 400 on surplus bytes), the connection is closed and on Windows loopback the client sometimes gets ECONNRESET before reading the reply (seen in my probes; the harness retried to see the 413). A browser fetch could then show a network error instead of the helpline JSON for an over-cap upload. Pre-existing with the old 256 KiB cap (server.ts readLimited calls `req.resume()` then the connection closes), unchanged by ISS-135, and reachable only by sending more than 64 KiB.
- NOTE (no issue): with a Content-Length smaller than the real body, Node's own parser may answer a bare `400 Bad Request` (no JSON, no helpline) to the surplus bytes before the handler answers. That is the http layer rejecting a malformed pipelined request, not the anonymous handler, and only a non-conforming client triggers it.
